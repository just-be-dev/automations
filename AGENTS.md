# Automations studio

A single-tenant prototype on Cloudflare: you design sequential automations in a chat, then run them in a Durable Object. Setup, deploy steps, and the HTTP API are in `README.md`. UI rules are in `src/ui/AGENTS.md`.

## Layout

- `alchemy.run.ts`: the Alchemy entry point, re-exporting `src/platform/cloudflare/stack.ts`. The stack declares the `Studio` Foldkit website, which carries Cloudflare Access and the test service token, and exports `StudioEnv`.
- `src/platform/cloudflare/`: all Cloudflare implementations and configuration. `api.ts` hosts the private `Api` Worker (`workersDev: false`), composes services per request, and implements the `AutomationNamer` with a fast Workers AI model; `automation.ts` hosts `AutomationAgent`, supplies storage, durable jobs and AI, and registers Alchemy callbacks. `automations.ts` adapts the namespace to the `Automations` service; `access.ts` extracts Access identity. Domain code must not import this directory, Alchemy, Cloudflare SDKs, or their native globals; `src/platform/boundary.test.ts` checks this.
- `src/http/api.ts`: platform-independent route composition. `automations.ts` owns automation routes and the overview, `entities.ts` owns entity routes, `catalog.ts` owns roles and templates (including which automations use a template, asked of each listed automation's `templateUses`), `mcp.ts` owns MCP transport, and `response.ts` shares boundary decoding and responses. Handlers use `Automations` and `RequestIdentity`, never a platform namespace or Access headers. The overview asks every listed automation's `overview` for its saved trigger, runs in flight, and latest run, and lists one that can't answer with its `error`.
- `src/automation/application.ts`: the automation facade. It composes `design-session.ts` (chat, pending replies, progress and draft permissions) and `runs.ts` (saved runs, human tasks and durable replay) over `workflow-store.ts` (snapshot reads, current catalog and saving). Each component captures its own services; neither lifecycle imports the other. The facade joins their reads for the studio. `workflow-store.ts` owns the complete save: validate, store the snapshot, update the trigger subscription, then best-effort update the directory. The snapshot and subscription cannot share a transaction; a subscription failure leaves the snapshot saved and is returned to the caller, and retrying save repairs the subscription. HTTP must not duplicate these writes. `host.ts` defines persistence and durable jobs as one capability: transactions must commit or roll back writes and scheduling together. `service.ts` defines `Automations`, the service callers use to address an automation. `chat` only stores the message as `pendingChat` and schedules the reply, so a reload mid-answer loses nothing; the UI polls until `pendingChat` clears. Progress stays in memory: pi's in-flight answer fixes some phrases, and `ProgressClassifier` picks the others from the planner's latest reasoning.
- `src/agents/planner/`: the planner agent. `planner.ts` holds its instructions, generated from the catalog, `planDraft`, which turns its edits and answer into a draft, and the progress phrases with the classifier question that chooses among them. `planDraft` sets the instructions as the root pi conversation's system prompt before each reply, so the catalog stays current, and sends each chat message as the user wrote it after the current draft in YAML (`turnMessage`). The planner never writes a whole workflow: it edits a working copy with the tools in `tools.ts` (`set_workflow`, `put_steps`, `remove_steps`, `set_permissions`, `show_workflow`, `check_workflow`, and the shared `ask_question`) and then answers in Markdown, which the studio renders. `plan.ts` holds that working copy: every step once in `stepsById`, with the lists inside parallel, if, and decide steps naming step IDs, so no tool argument nests steps. Every edit sets values or replaces steps by ID, so a tool call pi runs again after a restart changes nothing more. When the answer arrives, `assemblePlan` rebuilds the tree, and it must decode and check against the catalog; if not, the planner gets one retry with the problems. An answer that changed nothing leaves the draft as it is, so the planner can just ask a question. The questions are kept with the working copy, not in it, so asking never counts as a change.
- Asking parks the planner's pi turn, possibly for days, so nothing may wait on it. Callbacks run one at a time in the object's alarm, so `planReply` returns as soon as the turn parks (`AnswerHub.watchParked`) and writes nothing; the studio sees `pendingChat.status: "asking"`, derived from the working copy's unanswered questions, and the pending chat lists the rounds already answered in `asked` so the chat shows the answers before the reply is written. `answer` (`POST /api/automations/:id/answers`, or `chat` while asking) stores the answer and schedules `planReply` again in one transaction, then wakes a tool still waiting in memory (`AnswerHub.deliver`). If the object restarted, pi reruns the replay-safe tool when it reopens, and it finds the answer in storage under its pi call ID (`AgentToolCall.id`, the tool task's ID). The redelivered `planReply` joins the same pi turn through its request ID and writes the exchange with the questions and answers (`asked`). Whatever the planner reads of a workflow is YAML (`planYaml`); its tool arguments stay JSON. Progress is read by non-technical users: keep the phrases plain, and never let them reveal the retry or show the agent's raw reasoning. `progress-classifier.ts` defines the `ProgressClassifier` service the host implements. The chat lifecycle that calls the planner stays in `src/automation/design-session.ts`, and `src/automation/planning.ts` keeps the working copy in storage and builds the tools over it.
- `src/agents/namer/`: the namer agent. `nameAutomation` asks the `AutomationNamer` (a fast model) to title a new automation from its description, and falls back to the description's opening words if the model is slow, fails, or answers with nothing, so creation never fails on naming. `src/automation/creation.ts` (`createAutomation`, behind `POST /api/automations`) names the automation, lists it, and sends the description as its first chat message; if that message can't be sent, the automation stays listed and the response has no `pendingChat`.
- `src/automation/model.ts`: chat exchanges, pending messages, and automation list/overview schemas.
- `src/automation/run-store.ts`: owns persisted application runs (`StoredRun`, the public `Run` schema with its ID branded internally), serialized updates from parallel reports, settlement from engine outcomes, and execution-to-run lookup. Only the durable engine owns the replay journal; never use a run record to seed interpreter working values. `RunId` and `ExecutionId` are distinct branded strings. HTTP paths, storage reads and job callbacks decode them without changing their wire values.
- `src/workflow/model.ts`: the pure DSL. It holds the Schema models (`Workflow`, `Trigger` (manual, entity, schedule, or date), the recursive `Step` tree), `{{ref}}` template strings, and condition evaluation, including an action's `template` use and `match`. `src/workflow/run.ts` owns the public run record, step results, human tasks, and run summaries. `src/workflow/execution.ts` owns `ExecutionValues`, the subject and completed step values rebuilt by the interpreter on each replay, and `ExecutionId`. `src/workflow/schedule.ts` checks a schedule trigger's cron expression, finds its occurrences in its time zone with Effect's `Cron`, decides which day a date falls on, and says them in words for the UI. `src/automation/subjects.ts` reads entities as run subjects, resolves refs through them, and picks the entities a timed trigger is due for; both save and the tick use it. `docs/workflow-dsl.md` is the reference; keep it in step.
- `src/entities/templates.ts`: the pure model of stored templates: approved wording with slots (`hire → employee`) whose `content` fills an action's text inputs. It checks a template against the entity types and expands the templates a workflow uses into plain inputs (`expandTemplates`). The code calls `{{ref}}` text a template string too; keep the two apart in names and docs.
- `src/entities/model.ts`: the pure entity model: entity types, records, checking data against a type, and reading a ref through `ref` fields.
- `src/connections/registry.ts`: the registry of connections and their operations. It is pure, so the planner, the checker, and the UI all read it. `src/connections/runner.ts` executes the operations.
- `src/workflow/catalog.ts`: checks a workflow against the entity types, templates, and connections (refs, step ordering, operation inputs on every path through a match, template slots), and describes them to the planner.
- `src/workflow/interpreter.ts`: `RunAutomation`, an `effect/workflow` Workflow whose payload is a saved workflow and its subject. It walks the step tree with Activities, DurableClocks, and DurableDeferreds, and reaches the outside world only through the `StepRunner` service. Code outside an Activity reruns on every replay, so keep it deterministic.
- `src/workflow/durable-engine.ts`: a replaying `WorkflowEngine` that journals into a key-value store, the Automation object's storage. It never keeps a run in memory between events; the host replays on `wake` and fires clocks on `wakeAt`.
- `src/workflow/agent-step.ts`: the prompts for agent and decide steps, and how their answers become records.
- `src/automation/index.ts`: the `AutomationIndex` service, with its layer in `src/platform/cloudflare/automation-index-d1.ts`. Cloudflare can't enumerate Durable Object names, so each automation is recorded there when the studio creates it (`listNewAutomation` picks a free ID from its name), when the agent writes a draft and on save (both rename it to the draft's name), and, if it's missing, when an existing automation is opened. It backs `GET /api/automations`.
- `src/http/entity-mcp.ts`: the entity store's MCP tools and stateless JSON-RPC answerer. Its tools are an Effect `Toolkit` whose handlers run over the request's `EntityStore`. Effect's `McpServer` doesn't fit here: it keeps sessions in memory and runs handlers on a fiber outside the request, where D1 can't be reached. `put_entity` notifies subscribers through `EntitySubscribers`, which `Api` provides, so it starts runs exactly like `PUT /api/entities/...`. `list_roles` and `define_role` manage roles like `/api/roles`.
- `src/entities/store.ts`: the `EntityStore` service, which keeps entity types, entities, templates (checked against the types when written), roles (who approves operations that ask first), and which automations subscribe to each type. Saving an automation subscribes it to the entity type its trigger names, which keeps the type from being deleted; only entity triggers start runs on a change. Its operations are built over a small `EntityStorage` interface, so every implementation merges and validates alike; `layerMemory` is the in-memory one for tests.
- `src/entities/subscribers.ts`: `EntitySubscribers`, shared by HTTP and MCP entity writes. Its layer captures `EntityStore`; the host supplies the notification operation for one automation. Each subscriber's result or error is returned without preventing the others from being notified.
- `src/platform/cloudflare/entity-store-d1.ts`: `EntityStoreD1`, the store's D1 layer. Like `AutomationIndexD1`, yield it in the outer Effect (it binds D1) and provide the layer it returns per request or per instance (it needs a `RuntimeContext`). Service methods capture that context and have no runtime requirements. Code that reads or writes entities depends on `EntityStore`, never on D1.
- `src/platform/cloudflare/database.ts`: the shared `AutomationsDatabase` D1 resource declaration.
- `src/workflow.ts`, `src/entities.ts`, `src/connections.ts`: public domain re-exports that preserve the UI's imports. Backend code imports the owning modules directly.
- `migrations/`: D1 migrations, applied in numeric order on deploy and under `alchemy dev`.
- `src/ai/ask-question/`: the `ask_question` tool, for any agent whose host can show the person questions. `tool.ts` builds it from an `Ask` function the host supplies; `question.ts` holds the questions (1–4, each with 2–4 options), their answers, the checks that list every problem in plain words (`questionnaireProblems`) so the model fixes them in one call, and the result text the model reads (`answerResult`). The tool blocks until the person answers, so the agent carries on in the same turn. The studio walks the person through the questions one at a time and offers a "Write your own answer" row on each (which is why "Other" is a refused label); they can also skip them, or type in the composer instead, which answers as a message. `answer-hub.ts` is the per-instance `AnswerHub` that wakes a parked turn. The planner is the only agent that uses it today: `src/automation/planning.ts` supplies its `Ask`, keeping each call's questions and answer in the working copy.
- `src/ai/pi.ts`: the `PiAgent` conversation service contract, and `AgentTool`, a tool the root conversation can call. `transcript` reads a conversation back as a `Trace` (`src/ai/trace.ts`): its system prompt changes, prompts, model responses with reasoning, tool calls and token use, and tool results. `GET /api/automations/:id/trace` serves the planner's (the root conversation) and `GET /api/automations/:id/runs/:runId/trace` the one a run's agent steps share (the run's `conversation`); both are read-only. `src/platform/cloudflare/pi.ts` and `pi-storage.ts` implement it with pi-durable and pi-ai inside the Durable Object, with pi's tables stored in the object's SQLite. The tools are installed as one pi extension that only the root conversation selects, so agent steps never see them; the Automation object builds them before opening pi, so an answer resumed after a restart still has them.
- `src/platform/cloudflare/edge.ts`: the Studio Worker's async entry. It only forwards `/api/*` to `Api`. Keep logic out of it.
- `src/ui/`: the Foldkit browser app. `src/ui/route.ts` maps URLs to its pages: `/` is the overview (`src/ui/page/overview/`, a Submodel that lists runs in flight and starts saved automations), `/?automation=<id>` is the studio that edits one, and `/?automation=<id>&run=<runId>` is a run's page. The studio and run pages belong to the root app: its state is in `src/ui/model.ts`, and its update and view are split by area under `src/ui/update/` and `src/ui/view/`. A run page shows the snapshot the run executed and never the planner chat or the draft. The sidebar's + opens the new automation dialog (`update/new-automation.ts`, `view/new-automation.ts`, the foldcn Dialog submodel); creating one adds it to the sidebar before the list reloads, then opens it. The header shows the open automation's name. On the overview and in the studio, a plain click on a run link opens the run in a side panel instead (`maybeRunPanel`); the panel and the run page share the `OpenRun` state, and changing pages closes the panel. `GET /api/automations/:id/runs/:runId` returns the run with its `subjectTitle`, so either view labels it without another request. Agent replies render through `src/ui/components/markdown.ts`, which builds elements from marked's tokens and never sets HTML, so raw HTML shows as text and links open only web and mail addresses. Step results render through `src/ui/components/record.ts` as labelled fields with readable dates; people using the studio don't read JSON, so run views never show it raw (the draft's JSON toggle is for designing). `/templates` (`src/ui/page/templates/`, a Submodel) lists, creates, and edits templates and shows which automations use the open one; a step's template chip in the studio links there. `/entities` (`src/ui/page/entities/`, a Submodel) is a debug page for the entity store, and `/traces?automation=<id>&run=<runId>` (`src/ui/page/traces/`, a Submodel) is the debug page for agent traces: an automation's planner, or a run's agent steps. Every page change bumps the model's `revision`, so the previous page's polls and late replies are dropped. `public/_headers` sets the CSP for static assets.


- Tests use `bun:test` and sit next to the code they cover. Run Effects with `Effect.runSync` or `Effect.runPromise`.

## Debugging a user's automation

The UI keeps the open automation, and its open run, in the URL (`/?automation=<id>&run=<runId>`). When a user shares that URL from `mise run dev`, read the automation over the local API. Dev mode skips Access, so no credentials are needed:

```sh
curl -s "$STUDIO_URL/api/overview"                       # every automation's trigger and runs in flight
curl -s "$STUDIO_URL/api/automations"                    # every automation with a draft
curl -s "$STUDIO_URL/api/automations/<id>"               # draft, saved, conversation, recent runs
curl -s "$STUDIO_URL/api/automations/<id>/runs/<runId>"  # one run: steps, records, tasks; the UI shows the run ID
curl -s "$STUDIO_URL/api/automations/<id>/trace"         # the planner's prompts, reasoning, and tool calls
curl -s "$STUDIO_URL/api/automations/<id>/runs/<runId>/trace"  # what the run's agent steps were asked and answered
curl -s "$STUDIO_URL/api/entities/types"                 # entity types
curl -s "$STUDIO_URL/api/entities/<type>"                # a type's entities
```

Stick to these `GET` routes unless the user asks for more. `chat` calls Workers AI and replaces the draft, `save` and `start` change what runs, answering a task moves a run on, `PUT /api/entities/...` (and MCP's `put_entity`) can start runs, and `DELETE` routes remove data.

## Effect

- Before writing Effect code, run `bunx effect-solutions list`, then `bunx effect-solutions show <topic>` for the patterns you need.
- Import from bare modules, e.g. `import * as Effect from "effect/Effect"`.
- New Worker and Durable Object code is Effect-native.
  - Decode every boundary with Schema: request bodies, path params, LLM output, and values read back from storage.
  - Model expected failures with `Schema.TaggedError`.
  - Name operations with `Effect.fn("Module.operation")`.
- Durable Object RPC errors reach the Worker as plain objects. Map them structurally (see `messageOf` in `src/http/response.ts`); don't use `instanceof`.
- pi-ai and pi-durable stay on purpose even though they are Promise-based. Wrap them in `src/platform/cloudflare/pi.ts` with `Effect.tryPromise` and `PiError`. Don't swap them for Effect AI.

## Alchemy 2

- Alchemy 2 is a beta Effect API, and the v1 (`await alchemy(...)`) docs don't apply.
  - Docs index: https://alchemy.run/llms.txt (append `.md` to a page URL to get markdown).
  - The installed source in `node_modules/alchemy/src` is the final reference.
- Each Worker and Durable Object has two phases:
  - The outer Effect runs at plan time and at cold start. Keep it to binding calls such as `yield* Automation` and `Cloudflare.Workers.AI()`.
  - The inner Effect or handler runs per instance or per request. Storage, the AI binding's `raw`, and callbacks are only usable there.
- Plan time imports `alchemy.run.ts` and everything it reaches under Bun. Never import a module that loads `cloudflare:*` at top level. This is why `src/platform/cloudflare/pi-storage.ts` replaces `agents/harness/pi`.
- `Alchemy.makeCallback` delivers at least once. Keep handlers idempotent:
  - A replay only reruns what the engine's journal lacks. Agent steps use the pi `requestId` `agent:<key>`, where the key is the Activity's idempotency key including the attempt, so a retry asks again but a replay doesn't. Action steps pass a key that stays the same across retries to the operation, and `http.post` sends it as `Idempotency-Key`.
  - Chat replies reuse the pi `requestId` `chat:${chatId}`, and their retry `chat:${chatId}:retry`. A redelivery keeps the working copy the first delivery started for that chat ID. Only the delivery that still finds that message pending writes the exchange. Planner tools must stay idempotent.
  - Callback names and payloads are persisted contracts. Keep them compatible: `planReply` `{ automationId, chatId }`, `advance` `{ executionId }` (jobs from before entity-based triggers carried `{ runId }` and are ignored), `clock` `{ executionId, deferredName }`, and `tick` `{ at }` under the job ID `schedule`.
  - A timed trigger's (`schedule` or `date`) `tick` starts each occurrence's runs under IDs fixed by its time and subject (`scheduled-<at>`, `scheduled-<at>-<entity id>`), so a redelivery finds them instead of starting them again, then books the next occurrence. A date trigger ticks daily at its time. Saving books or cancels the tick in the same transaction as the snapshot.
  - An occurrence never starts only some of its runs: past `MAX_SCHEDULED_RUNS` it starts none and records a failed `scheduled-<at>` run saying why, and save refuses a trigger that already matches more. Keep it that way; don't trim the list.
- Storage keys are persisted contracts too: `draft`, `saved`, `pendingChat`, `plan` (the planner's working copy for one chat ID, with each `ask_question` call's questions and answer by call ID), `run:<id>`, `execution:<executionId>` (its run ID), `exchange:<000000>`, and `exchangeCount` in `Automation`, plus the engine's journal under `wf:<executionId>:` (see `src/workflow/durable-engine.ts`). Workflows and runs from before entity-based triggers don't decode; reading one drops it.
- Activity and deferred names in `src/workflow/interpreter.ts` (`<id>`, `<id>/refs`, `<id>/now`, `<id>/request`, `<id>/outcome`, `<id>/timeout`, `<id>/approval-request`, `<id>/approval`) are journal keys for runs in flight. Renaming one makes a waiting run redo that step.
- Never edit an applied D1 migration. Add the next numbered file in `migrations/` instead; Alchemy tracks applied files by hash in `__alchemy_migrations`.

## Invariants

- `isPublicHttpsUrl` in `src/workflow/model.ts` is the SSRF boundary. `http.post` URLs must be literal (no templates), HTTPS, without credentials, and target no private or loopback host. The catalog checks them when a workflow is checked, and the connection runner checks again before sending. Don't loosen either without tests.
- Runs always execute the saved snapshot, never the draft. Workflows must not contain secrets; connections will hold credentials.
- A run starts by checking the saved workflow against the current catalog and expanding its templates (`beginRun` in `src/automation/runs.ts`). The run's payload carries the expanded workflow, so replays never read a template; the interpreter fails an action that still uses one.
- The planner prefers templates to writing text or adding agent steps that write it. Keep that guidance in `plannerInstructions` when changing the prompt.
- The planner suggests permissions and the person can change them; both merge into the draft's `permissions`. The planner reads the current draft, permissions included, on every turn so it keeps the person's changes. Every operation a workflow uses needs one: `"auto"`, or `{ "ask": "<role>" }` naming a role in the entity store.
- Only a role's members answer its approval tasks. `Api` passes the Cloudflare Access email to `Automation.respond`, which checks it against the members the task recorded when it was opened.
- A step that didn't run (declined or skipped) records nothing, and the interpreter skips any step that needs its record (`stepNeeds`). That relies on the checker's guarantee that every step a ref names finishes before the reader on every path. Don't loosen one without the other.
- `http.post` doesn't forward trace headers.
- Email, Slack, and Calendar are simulated until they have credentials: they contact nothing and record `simulated: true`. Say so wherever results are shown.
- `/api` keeps a 32 KB request-body limit and returns `{ "error": string }` on failure. The UI relies on that shape.
- `Api` stays private. Only the Access-protected Studio Worker can reach it.

## Deploy and dependencies

- Never run `alchemy deploy`, `alchemy destroy`, or `alchemy dev --stage <deployed stage>` unless asked.
- `alchemy dev` runs locally on stage `dev_$USER`, skips Access, and still needs a Cloudflare profile for Workers AI. Its state lives in the checkout's `.alchemy/state` beside the local data, so each worktree migrates its own database. Deploys use the Cloudflare state store.
- Never commit `.alchemy/` or Access service-token secrets.
- Foldkit, `@foldkit/*`, Vite, and `@effect/platform-*` are pinned exactly on purpose. To upgrade Foldkit, follow `src/ui/AGENTS.md`.
- Patch dependencies only with `bun patch`. Document every patch in `patches/README.md`: the symptom, the cause, what the patch changes, and the upstream fix that would let you remove it. When you upgrade a patched package, recheck its patch.
